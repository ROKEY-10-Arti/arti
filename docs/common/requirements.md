# 요구사항 요약 (개발용)

원본은 [팀 노션](https://app.notion.com/p/ROKEY-10-1-Art-I-4179fb50923980e69d41f317a16cc003)의 BR(11.14), SR(11.14–15), 시나리오, 플로우차트다.
이 문서는 **코드에 영향을 주는 내용만** 추려서 패키지에 대응시킨 것이다. 원본이 바뀌면 여기도 고친다.

## 1. 기능 → 패키지 매핑

| 기능 | 핵심 동작 | 담당 패키지 |
|---|---|---|
| 서비스 시작 | 갤러리 소개, 사용법 이미지 슬라이드, 모드 선택 (코스 안내 / 자유 관람) | 키오스크 UI (Figma) |
| 로봇 배정 | 운행 가능한 로봇 중 **배터리 최고** 로봇 배정, 둘 다 사용 중이면 대기열 | `arti_fleet` |
| 만남 | 언도크 → 만남 위치 이동 → 관람객 등록(재식별 가능하게) | `arti_fleet`, `arti_follow` |
| 코스 안내 | 추천 코스 / 작품 검색(제목·작가·테마) → 핀 → 방문 순서 경로 | 코스주행 담당 (이 저장소에 아직 없음) |
| ↳ 속도 조절 | 관람객이 뒤처지면 감속·대기, 다른 통로로 가면 정지 + 재합류 안내 | 코스주행 담당 (사람 인식은 `arti_follow` 결과 공유 예정) |
| 자유 관람 | 등록한 관람객을 **약 80cm** 유지하며 추종 | `arti_follow` |
| ↳ 분실 처리 | 마지막 좌표로 이동 → 회전 탐색 → 대기 → 재등록 안내 | `arti_follow` |
| 작품 해설 | 작품 관람 구역(반원)에서 **약 5초** 정지하면 에어팟으로 해설, 떠나면 중단 | `arti_docent` |
| 장애물 | 우회, 불가하면 정지 | Nav2 (파라미터는 `arti_bringup`) |
| 통로 겹침 | 먼저 진입한 로봇 우선, 동시 도착 시 관제가 순서 부여 | `arti_fleet` |
| 배터리 | 부족하면 신규 배정 제외, 이용 중 부족하면 안내 종료 → 도킹 → 다른 로봇 투입 | `arti_fleet` |
| 이상 감지 | 넘어짐·들림 등 구동 불가 → 관제 PC 로그 + 직원 호출 | `arti_fleet` |
| 이용 종료 | 화면에서 종료(코스는 마지막 작품에서 자동), 구매 의사 확인 → 직원 연결, 배정 해제 → 충전 위치 복귀 | `arti_fleet`, UI |
| 운영자 | 일시정지·재개·복귀, 비상 정지(화면 + 로봇 본체) | `arti_fleet`, 관제 UI |
| 작품 마킹 | 작품 밑 AprilTag → art ID / pose 등록 | `arti_follow` |

## 2. 수치 요구사항 (테스트 기준)

| 항목 | 기준 |
|---|---|
| 추종 거리 | 약 80cm |
| 해설 시작 | 관람 구역에서 약 5초 정지 (통로에서 잠깐 멈춤·일행 대기는 제외) |
| 충돌 위험 → 정지 명령 | 200ms 이내 |
| 감상 구역 이탈 → 해설 중단 | 2초 이내 |
| 화면 응답 | 1초 이내 |
| 추종 정확도 (수락 기준) | 95% 이상 |

## 3. 설계 제약

- **개인정보:** 관람객 영상은 저장하지 않고 실시간 처리만 한다. 추적용 특징(re-ID feature)은 세션 종료 즉시 폐기한다. rosbag으로 카메라 토픽을 녹화할 때 주의해야 한다.
- **확장성:** 로봇 추가, 지도, 작품 위치, 관람 구역은 **코드 수정 없이 설정 파일(YAML)** 로 바꿀 수 있어야 한다. 하드코딩하지 않는다.
- **통신 단절:** 통신이 끊기면 안전하게 정지한다. 복구 후에는 관람객과 경로를 다시 확인하고 재개한다.
- **안전:** 작품 보호 구역에는 진입하지 않는다. Nav2 keepout 필터 후보.
- **연산:** 로봇 내부 컴퓨터(RPi)는 성능이 낮다. YOLO 같은 무거운 처리는 PC에서 실행하는 방향을 검토한다.

## 4. 하드웨어·네트워크 메모 (11.15 기준)

- 카메라: TurtleBot 4 **위에 올린 노트북 웹캠을 탑CAM으로 사용**한다 (`video_source:=0`, 휴대폰 DroidCam URL도 가능). 깊이(Depth)는 OAK-D를 쓴다.
- 카메라 위치를 TF로 등록했다. LiDAR와 합쳐 사람 위치를 map 좌표로 변환한다. 위치는 대체로 정확하지만 값이 튀는 노이즈가 있다 → 필터가 필요하다.
- 네트워크 사용량(기본 TB4 토픽 + 휴대폰 카메라 + LiDAR): 총 8–9 MB/s. 휴대폰 카메라 2 MB/s 이내, 노트북 웹캠 500 KB/s 이내, LiDAR 4–6 MB/s로 추정. Nav2 등을 추가하면 다시 측정해야 한다.
- 지도: `maps/gallery.{pgm,yaml}` (저장소 루트) (66 x 121 px, 0.05 m/px → 약 3.3 m x 6.05 m).

## 5. 범위 밖 (MVP)

결제, 음성 대화형 질의응답, 단체 관람(여러 명 동시 추종), 이어폰·다국어 해설, 이전 작품으로 되돌아가기(미결), 실제 갤러리 설치.

## 6. 미결 사항 / 위험

- 앞 그룹을 앞지를 때 추종 대상을 잃는 문제
- 앞·뒤 그룹이 같은 작품을 보려는 경우 → 작품 상태 관리를 거쳐 Nav2 목표를 조정
- 좁은 통로에서 두 그룹이 섞이는 경우, 한 작품 앞에 관람객이 몰려 막힌 경우 → 완화책 미정
- 인접한 두 작품 중 어느 쪽을 보는지 애매하면 화면에서 선택하도록 안내

## 7. 개발 순서 (사용자 추종 플로우차트 기준)

1. 기반 준비 (공통/환경)
2. 관람객 등록 — 스캔 시작 → 탑CAM 인식 → 등록 → 성공 보고
3. 위치 추정 — 지속 재식별 → 탑CAM·Depth 매칭 → 거리 측정 → map 좌표
4. 추종 주행 — 80cm 유지
5. 작품 설명 — 5초 정지 → 반원 구역 판정 → 설명 / 이탈 시 중지
6. 분실 처리 — 최종 좌표 이동 → 회전 탐색 → 대기 → 재등록
7. 종료·복귀 — 배터리 부족·종료 구역 → 종료 보고 → DOCK
8. 안정화·통합 테스트
